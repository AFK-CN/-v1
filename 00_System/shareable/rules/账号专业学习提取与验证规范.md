# 账号专业学习提取与验证规范

本规范是 `账号专业学习Skill_v2` 的 v2.2 阶段产物说明。只在执行账号学习七阶段流水线时读取。

单条内容先按 `统一学习卡产出标准.md` 生成 `unified_three_layer_v2` 学习卡。单卡中的 RIA++ 只是方法候选；本规范负责跨卡验证和完整方法沉淀。

## 阶段 0：整体账号理解

`ACCOUNT_OVERVIEW.md` 必须包含：

- `## 1. 账号结构`：账号类型、一句话主旨、3-7 个内容支柱及关系、核心受众问题。
- `## 2. 关键术语与定位`：账号反复使用的概念、具体含义、与行业常见说法的差异。
- `## 3. 批判与偏差`：样本期、平台、商业合作、幸存者偏差、证据缺口等至少 3 项。
- `## 4. 学习应用潜力`：哪些规律可能形成方法单元，哪些只适合作为案例或背景。

`ACCOUNT_OVERVIEW.json` 最小结构：

```json
{
  "one_line_theme": "一句话主旨",
  "content_pillars": ["支柱1", "支柱2", "支柱3"],
  "terminology": ["术语1", "术语2", "术语3"],
  "limitations": ["局限1", "局限2", "局限3"],
  "evidence_refs": ["source_id或原链接1", "source_id或原链接2"]
}
```

## 阶段 1：五视角提取

五个提取视角必须独立判断，避免沿用上一视角的筛选结论：

1. `positioning`：受众、承诺、身份视角、价值边界、商业与非商业边界。
2. `topics`：稳定问题域、选题母题、热点使用方式、系列化与避题规律。
3. `structures`：标题、开头、论证、案例、行动、收尾之间的可重复结构。
4. `expression`：叙事距离、口语信号、具体化方式、视觉/镜头/图文组织、去模板化规律。
5. `counterexamples`：失败内容、矛盾证据、过度承诺、单例误判、商业污染与不适用场景。

每个 JSONL 候选最小结构：

```json
{"id":"p01","title":"候选方法","type":"positioning","source_refs":["xhs_001"],"summary":"用自己的话解释","tags":["定位"]}
```

本阶段宁可保留候选，不做录取判断。重复项在阶段 2 合并，所有 source refs 必须保留。

五个视角是一个方法的不同证据角色，不等于五类都要各自生成方法。定位、选题、结构和表达可以共同组成一个机制簇；反例优先作为边界或证据门，不默认晋升成可调用方法。

五个视角从统一卡中读取的重点：

- `positioning`：证据边界、核心观点、受众与价值承诺。
- `topics`：核心观点、可复用选题与案例、发布内容层。
- `structures`：动态内容结构、媒体表现层、可复用模板。
- `expression`：金句与表达素材、发布文案、媒体表现层。
- `counterexamples`：商业隔离、证据缺口、RIA++ 候选 B 段。

### 阶段 1 的深层结构与表达观察

新工作流使用 `deep_structure_expression_v1` 派生观察。该观察建立在学习卡和必要源证据之上，不修改 `unified_three_layer_v2`，也不要求历史卡迁移。旧工作流和旧候选继续按兼容模式读取。

`structures` 可以检查以下观察维度，但不得机械凑齐：

- `concrete_entry_or_commitment`：从什么具体时刻、承诺、问题或结果进入。
- `initial_problem_or_context`：观众理解后续内容所需的初始语境。
- `concrete_actions`：人物、项目或讲述者做了什么。
- `obstacle_or_conflict`：什么阻力、误解、失败或限制推动内容继续。
- `turning_point`：认知、行动或结果在哪一步发生变化。
- `result_or_feedback`：可观察结果、他人反馈或验证信号。
- `abstraction_entry`：观点、模型或道理在什么时机进入，而不是是否出现。
- `beneficiary_closure`：内容如何回到受众判断、行动或下一步。

以上只是通用观察坐标，不是八段固定模板。账号可以缺少其中若干项，也可以出现新的结构单元；缺失项写入 `missing_or_uncertain_units`，不能补造。

结构候选的增强字段示例：

```json
{
  "id": "str-01",
  "type": "structures",
  "observation_schema": "deep_structure_expression_v1",
  "observation": {
    "status": "single_card_observation",
    "dimensions_considered": ["initial_problem_or_context", "concrete_actions", "obstacle_or_conflict", "result_or_feedback"],
    "observed_units": [
      {"unit": "initial_problem_or_context", "evidence": "证据摘要", "source_coordinate": "source-01#transcript:12-18"}
    ],
    "unit_order": ["initial_problem_or_context"],
    "missing_or_uncertain_units": ["concrete_actions", "obstacle_or_conflict", "result_or_feedback"],
    "evidence_coordinates": ["source-01#transcript:12-38"],
    "structure_fingerprint": "问题语境>行动>受阻>结果；单卡草案，待多卡验证"
  }
}
```

`expression` 可以检查以下观察维度：起话方式、长短句与停顿节奏、口语连接和自我修正、与观众的关系、具体细节密度、故事与解释配比、抽象解释进入时机、利他落点、反模板信号。不得只用词频、口头禅或“多用短句、更加口语化”等泛化建议替代证据。

表达候选的增强字段示例：

```json
{
  "id": "exp-01",
  "type": "expression",
  "observation_schema": "deep_structure_expression_v1",
  "observation": {
    "status": "single_card_observation",
    "dimensions_considered": ["opening_voice", "sentence_rhythm", "concrete_detail", "abstraction_timing", "beneficiary_landing"],
    "observed_signals": [
      {"signal": "concrete_detail", "evidence": "具体人物动作与结果先于观点", "source_coordinate": "source-01#transcript:12-30"}
    ],
    "missing_or_uncertain_signals": ["opening_voice", "sentence_rhythm", "abstraction_timing", "beneficiary_landing"],
    "evidence_coordinates": ["source-01#transcript:12-45"],
    "expression_fingerprint": "先讲具体经历，再解释原因；单卡草案，待多卡验证"
  }
}
```

派生观察必须满足：

- `observed_units` / `observed_signals` 只保存本条能回查的现象。
- `evidence_coordinates` 优先使用逐字稿行号、时间码、帧号或图文页码；只有卡片时可记录卡片章节并标记兼容证据。
- `structure_fingerprint` / `expression_fingerprint` 只是单卡序列摘要，不是账号稳定规则。
- 单卡观察保持 `callable=false`，不得在阶段 1 命名账号结构家族。

### 阶段 1A：真实验收门

五视角提取完成后、阶段 2 聚类前，必须生成 `REAL_ACCEPTANCE_REPORT_<date>.md` 和 `REAL_ACCEPTANCE_SUMMARY.json`。机器摘要至少记录：

- 可重复抽样方法与抽中的 `source_id`。
- 正常视觉、正常长逐字稿、商品广告、平台项目、合拍归属、低信息或 ASR 风险六个分层的验收状态；没有对应样本时必须写 `not_applicable` 和原因。
- 严重问题数量、同类全量扫描或扩大抽样是否完成。
- 跨字段语义一致性是否通过。
- 账号总览覆盖数、实际学习数和状态文件数量是否一致。
- 商品广告、平台项目的总数、已完成源证据审计数及对应索引路径。
- `formal_write=false`、`callable=false`。

真实验收不是随机阅读几张卡。每个抽中样本必须回到逐字稿、源视频、抽帧或原始发布层证据；发现严重问题后必须验证同类全集，不能只修抽中项。

### 正常、商品广告、平台项目三轨分流

- 正常内容：可以进入自然选题频次和自然方法 V1。
- 商品广告：不得进入自然频次和自然方法 V1，但逐条生成植入学习记录，保留广告前正常剧情、引入桥、产品剧情角色和广告后收束。
- 平台项目：挑战赛、栏目、活动、晚会、纪录片和平台策划单列，学习其项目壳、参与方式、人物证据和发布协同，不与商品广告混合。

广告引入桥至少区分：`same_engine`、`reveal_payoff`、`role_need_or_prop`、`world_feature`、`payload_takeover`。集中口播接管默认低融合，除非源证据能证明广告段仍推动原人物冲突。

逐字稿结论记录文本路径和行号。声称画面出现某动作、商品、品牌、活动页面或购买利益时，必须记录视频时间码或帧号；只有文本证据时标记为文本判断，不得改写成视觉核验。

## 阶段 2：三重验证

三重验证前先生成 `candidate_clusters.jsonl`，把阶段 1 的观察项聚合成机制簇。每条阶段 1 候选必须恰好进入一个机制簇，不能遗漏或同时进入多个簇。

每个机制簇至少包含：

```json
{
  "id": "cluster-001",
  "title": "机制簇标题",
  "cluster_type": "method_candidate",
  "core_mechanism": "不依赖来源人物、场景和道具的因果机制",
  "candidate_ids": ["top-01", "str-01", "exp-01", "counter-01"],
  "source_refs": ["source-01", "source-02"],
  "lens_roles": {
    "method_core": ["str-01"],
    "support": ["top-01", "exp-01"],
    "boundary": ["counter-01"],
    "evidence_gate": []
  }
}
```

新工作流的 `method_candidate` 还必须包含 `mechanism_kind`。当成员中存在 `structures` 或 `expression` 候选时，必须增加 `production_analysis`：

```json
{
  "mechanism_kind": "content_structure",
  "production_analysis": {
    "fixed_elements": ["跨样本稳定出现的单元或顺序"],
    "variable_elements": ["可替换的题材、人物、场景或表达实现"],
    "tension_engine": "为什么观众愿意继续看",
    "trust_engine": "为什么观众相信",
    "understanding_engine": "复杂内容如何被理解",
    "beneficiary_engine": "观众最终得到什么判断或行动",
    "length_basis": "内容完成取决于哪些信息闭环，不使用固定时长代替",
    "boundaries": ["反例、不适用场景和证据不足处"]
  }
}
```

`mechanism_kind` 只描述当前机制簇的作用，可以是 `positioning`、`topic_system`、`content_structure`、`expression_fingerprint` 或 `composite`，不是预设账号必须拥有的结构分类。结构家族的数量和名称必须由多卡相似序列聚合、固定/可变比较和反例拆分产生；不同账号可以得到不同数量和完全不同的结构。

`cluster_type` 只允许 `method_candidate`、`boundary_rule`、`evidence_gate`。只有 `method_candidate` 可以进入 verified；边界规则和证据门保留在拒绝/边界集合中，但不得丢失。

只有三项全部通过的 `method_candidate` 机制簇进入 `verified.jsonl`：

- V1 `v1_cross_context`：至少 3 个独立正常内容并跨 2 类关系或场景支持，不得把商业/平台样本、同系列近重复，或同一条内容的标题、正文、逐字稿重复计数。
- V2 `v2_predictive_usefulness`：使用未见任务盲测，能指导一个样本中没有直接给答案的新选题、新脚本或新判断，并给出非平庸的结构性预测。
- V3 `v3_account_exclusivity`：是该账号可辨识的稳定规律，不是“标题要吸引人”等平台常识。

通过项结构：

```json
{
  "id": "p01",
  "title": "候选方法",
  "triple_verification": {
    "v1_cross_context": {"passed": true, "reason": "理由", "evidence_refs": ["xhs_001", "douyin_002", "douyin_003"], "relation_or_scene_types": ["职场", "家庭"]},
    "v2_predictive_usefulness": {"passed": true, "reason": "未见任务及结构性预测", "blind_task_id": "blind-001"},
    "v3_account_exclusivity": {"passed": true, "reason": "与行业常识的差异"}
  }
}
```

拒绝项写入 `rejected.jsonl`，最少包含 `id`、`title`、`failed_checks`、`reason`、`disposition`。`disposition` 用于区分真正拒绝、保留边界和等待证据。每个机制簇必须恰好出现于通过或拒绝集合之一。

## 阶段 3：RIA++ 方法单元

每个通过项建立 `methods/{id}/METHOD.md` 和 `method.json`。

`METHOD.md` 固定六段：

- `## R - 原始证据`：短引用或准确证据摘要，标注 source_id、原链接或时间戳。
- `## I - 方法论解释`：用自己的话解释账号规律，不照抄文案。
- `## A1 - 已发生案例`：问题、使用方式、结果、证据边界。
- `## A2 - 未来触发场景`：何时在新内容任务中调用。必须分别写触发机制、适用关系、可迁移场景和不触发条件；来源选题、人物、场景和道具不能直接充当触发器。
- `## E - 可执行步骤`：逐步动作、完成标准、判停条件。
- `## B - 边界与反例`：不适用场景、失败模式、样本局限、邻近方法区别。

`method.json` 最小结构：

```json
{
  "id": "p01",
  "schema_version": "2.1",
  "version": 1,
  "status": "verified_candidate",
  "callable": false,
  "account_scope": "来源账号的稳定标识",
  "title": "方法标题",
  "trigger_signals": ["冲突因果、信息差、限制条件或结构机制信号"],
  "trigger_model": {
    "mechanism": "需要复用的抽象机制",
    "applicable_relations": ["已证实关系或可迁移关系类型"],
    "transferable_scenes": ["已证实场景或可迁移场景类型"],
    "do_not_trigger_on": ["只有人物、场景、道具或题材词相同"]
  },
  "do_not_use": ["反场景"],
  "execution_steps": ["步骤1", "步骤2"],
  "source_refs": ["xhs_001", "douyin_002"]
}
```

方法召回采用两级路由：先按正式状态、账号、内容形态和主任务方向做基础召回；再按 `trigger_model.mechanism` 做跨方向扩展。人物关系和场景用于判断如何迁移，不是单独的命中条件。召回必须在生成草稿前完成，不允许因草稿中偶然出现某个名词而中途追加方法。

卡片状态和方法状态必须分离：学习卡 `review_passed` 只表示卡片审核通过，不表示其中的方法可调用。单卡、五视角候选、机制簇、`verified_candidate` 和候选交付均保持 `callable=false`；只有现有正式审核流程明确批准后，方法才能变为 `approved_callable`。

阶段 5 必须增加 `cross_scene_transfer` 测试：更换来源人物、场景和道具后，核心机制仍成立时应触发；只保留来源名词但移除核心机制时不应触发。

## 阶段 4：链接

`METHOD_INDEX.json` 包含 `methods` 和 `relations`。关系只允许：

- `depends_on`：方法 A 使用前需要方法 B。
- `contrasts_with`：A 与 B 是不同情境下的备选判断。
- `composes_with`：A 与 B 经常组合使用。

不强行建立关系，不允许未知节点或自环。共享术语写入 `GLOSSARY.md`。

`METHOD_INDEX.json` 或配套编排文档还必须说明：一个任务只选一个主冲突方法；递进方法只能增加同一因果链的轮次与强度；表达、标题和视觉组织作为支持层后置；正常内容、商品广告和平台项目先分流再调用方法。多主方法组合必须逐个消融，删除任一方法后若输出没有结构性变化，则该组合不成立。

## 阶段 5：压力测试

每个方法至少包含一条 `should_trigger`、`should_not_trigger`、`edge_case`、`cross_scene_transfer` 和 `commercial_contamination`。`should_not_trigger` 中必须包含一条 `decoy_kind=lexical_overlap_without_mechanism`：保留来源人物、场景或道具词，但移除核心机制，预期不得触发。`cross_scene_transfer` 必须更换人物、场景和道具，同时声明保留的核心机制。`commercial_contamination` 必须证明增加广告样本不会提高自然方法 V1 权重。多个方法时，每个方法至少有一条 `should_not_trigger` 指向兄弟方法的 `sibling_method_id`。盲测时不向执行者泄露预期类型和答案。

`test-results.json` 必须记录 `executor`、`executed_at`、`prompt_set_sha256`、逐案例 `case_results`，再由逐案例结果计算 `total`、`passed`、`failed`、`pass_rate`。每条案例至少记录 `id`、`passed`、`actual_decision`、`evidence`。系统必须校验提示集哈希、案例 id 全覆盖和汇总值一致；只手工填写 100% 汇总通过率不得过门。通过率不是 100% 时回到阶段 3 修改触发、步骤或边界，不能只改测试结果。

## 阶段 6：候选交付

`LEARNING_DIGEST.md` 面向后续使用者总结已验证方法、证据边界、拒绝项和待补证据。`promotion_manifest.json` 必须满足：

```json
{
  "status": "ready_for_review",
  "method_ids": ["p01"],
  "formal_write": false,
  "callable": false,
  "user_review_required": true
}
```

该清单只向原有正式入库审核流程交接，不执行正式写入。

同时生成 `ACCOUNT_PRODUCTION_HANDOFF.json`，把已验证学习结果翻译为账号中心的更新候选：

```json
{
  "schema_version": "account_production_handoff_v1",
  "status": "ready_for_review",
  "formal_write": false,
  "callable": false,
  "user_review_required": true,
  "source_method_ids": ["p01"],
  "coverage": {
    "structures": "insufficient_evidence",
    "expression": "insufficient_evidence",
    "anti_ai": "insufficient_evidence",
    "production_templates": "insufficient_evidence",
    "acceptance": "insufficient_evidence"
  },
  "structure_library_candidates": [],
  "expression_fingerprint_candidates": [],
  "anti_ai_rule_candidates": [],
  "production_template_mappings": [],
  "acceptance_checks": []
}
```

候选映射关系：

- 结构家族、调用条件和篇幅完成条件 -> `内容生产使用说明.md`、`内容输出标准模板.md`。
- 表达指纹、口语节奏和故事/解释关系 -> `内容生产使用说明.md`、`减少AI味输出规则.md`。
- 反模板信号和替换方式 -> `减少AI味输出规则.md`。
- 不同结构如何进入成品字段 -> `内容输出标准模板.md`。
- 账号辨识度、口语、证据、利他落点和结构完成度 -> 对应账号的内容验收规则。

`coverage` 只允许 `verified` 或 `insufficient_evidence`。某项为 `verified` 时，对应候选列表必须非空；证据不足时允许列表为空，但必须在 `LEARNING_DIGEST.md` 解释缺口。该交接包仍是候选，不得直接覆盖正式账号文件。
