# 发布文案生产规则

## 证据与调用

- 本规则是正式方法 `m02`、`m04`、`m07` 的生产展开，不新增方法。
- 默认直接使用本文件；只有新任务超出既有结构或需要核对特殊写法时，才按方向读取 2–3 张正式卡的“发布内容层学习”。
- 不在日常生产中读取完整 `sqlite_tables.db`。数据库只用于补学审计；生产不得把原文全集加载进上下文。

## 交付文件契约

此项是用户交付偏好，不是账号原文方法。选题文件夹中的 `发布文案.txt` 只能包含以下三个一级区块；不得同时保留同名 `.md`：

```markdown
# 发布标题

【可直接复制的标题】

# 发布文案

【可直接复制的正文】

# 话题

【可直接复制的话题】
```

- 不在该文件中放食材清单、独立做法说明、图文页面计划、拍摄要求、发布前核对、执行口径或内部溯源。
- 食材份量、调味、火候和时间若是发布所需信息，直接自然地写入“发布文案”正文，不另建交付区块。
- 方法、source_id、证据边界和版本信息进入生产记忆或内部工作区，不进入用户要复制发布的文件。

## 先分正文轨道

1. 普通自然单餐：使用菜名分段和不对称详略。
2. 一周合集：使用周一至周日的餐单索引，不展开七套教程。
3. 成本餐：在自然菜谱骨架上增加有来源的逐菜价格与真实合计。
4. 设备餐：正文围绕备料、装锅或分层、温度/程序、中途状态和出锅结果。
5. 商品广告：先写拿掉产品仍成立的自然餐食，再用有简报和素材依据的进入点承接产品；广告段不得反过来定义自然语气。
6. 平台项目与备餐知识卡证据不足，不自行推导固定正文模板。

## 标题

- 普通单餐优先使用“独居一人食｜【本条唯一变量】”；变量可以是主菜、真实场景、设备或成本中的一个。
- 一周合集直接承诺“一周、不重样、合集或菜单索引”，不再硬套单餐标题。
- 原账号常出现减脂、自律和吃得干净等词，但新内容只有在事实与发布口径允许时使用；不能因为高频就自动添加功效承诺。
- 保留自然标点，不复制来源错字、重复字或过量感叹号。

## 普通单餐正文

1. “今天吃🍽️”是可选入口，不是每条必填。
2. 每道菜用 `emoji + 菜名` 建立扫描入口；只有真实记录存在时才在菜名后写价格或每百克热量。
3. 复杂菜用编号步骤，优先交付：
   - 必要备料或预处理；
   - 调味比例；
   - 火候与关键时间；
   - 可见结束状态，例如出汁、定型、变色、收浓或断生。
4. 简单菜只写必要动作、时间或结果；不为排版平均而扩写。
5. 生活化计量优先使用勺、半碗、少许、个或瓣；需要提高复刻精度时，在生活化单位后补 `g/ml`。不把每一项都写成实验参数。
6. 克重、时间、温度和调味必须来自真实执行或明确拍摄标准；执行标准发布前按实拍校正。
7. 允许 `ps.` 写真实的失败提醒、替换条件或口感差异；不写泛泛的营养和效果建议。

## 整篇信息密度回归

- 生产前读取 `publishing-copy-golden.md`，只继承其结构不变量，不照抄菜品、克重、时间、话题或生活场景。
- 主菜必须先给出一人份核心食材，再用编号步骤写清备料、调味、火候、关键时间和可见结束状态；不能退化成“少许、适量、炒熟即可”的摘要。
- 每一个 `emoji + 菜名/主食` 标题后都必须有对应做法、执行标准或结果；不得出现只有“蒸玉米”“米饭”等名称而没有内容的空段。
- 配菜和主食可以短，但必须让读者知道怎么做；详略由复杂度决定，不等于允许漏写。
- 碎碎念只能补充本餐的具体动作、口感或食物搭配感受，不能替代菜谱信息，也不能用“颜色好看、很有食欲、治愈自己”等泛化句掩盖正文缺失。
- 用户提供了既有合格稿时，把该稿作为本次最高优先级回归基线；先做整篇差异检查，再处理局部反馈。
- 完稿后必须运行 `scripts/validate_publishing_copy.py`；未通过不得交付，也不得登记为完成。

## 合计、碎碎念与收尾

- 价格、整餐合计、热量、知识小栏、读书笔记和碎碎念都是可选证据模块，不是固定尾巴。
- 自然单餐先完成菜谱信息，再判断是否需要附言；默认最多选择一种叙事附言，不把碎碎念与读书笔记合并成自创标题。
- 碎碎念使用 `✨碎碎念`：写当前可核实的小场景、动作、食物感受或用户提供的心情，通常 1–3 个自然短句；没有素材就不写。
- 读书笔记使用 `📖读书笔记——《书名》`：正文只保留一句短笔记。书名和内容必须来自用户提供、任务素材或已核对来源；不得编造原句，不复制账号旧帖书摘充当新内容。
- 不把书籍观点、食材变化和情绪结果强行串成散文比喻；读书笔记承担独立生活附言，不负责解释菜谱。
- `今天吃🍽️`、`ps.`、`小宝们`、互动提问和温柔感悟均为可选信号，不得机械组合成固定开头与结尾。
- 有真实生活素材时，碎碎念写当前可核实的小场景、动作或食物感受，控制在能自然说完的长度。
- 没有真实素材时，停在最后一道菜、真实合计或话题即可；不强行补“下班回家”“最近很累”“一个人也要好好爱自己”。
- 不把书摘、天气、同事、工作状态或个人习惯写成作者经历，除非用户提供。
- 不用统一提问制造互动。自然单餐证据没有显示结尾提问是稳定要求。

## 一周合集

- 用 `周1️⃣：主菜➕配菜➕蔬菜➕主食` 逐日列出真实组合。
- 合集正文的价值是比较和索引，不复制单餐做法。
- 只有真实发生的阶段变化、菜单说明或当周语境才可放在索引后；没有就直接进入话题。

## 商品广告

- 保留“自然菜谱块 → 真实产品进入点 → 有来源的商业信息 → 回到餐食结果”的分区。
- 产品功效、成分、价格、体验和购买利益只来自当次简报、素材或用户确认。
- 不把广告中的夸张口吻、品牌话术或虚构疲惫场景写入自然正文规则。

## 话题

- 话题服务账号人群、用餐场景、本条菜品和真实内容轨道。
- 菜品未出现、效果未证明或活动未参加时，不添加相应话题。
- 话题是检索层，不用来补正文没有兑现的减脂、营养、健康或省钱承诺。

## 防模板检查

- 各菜段落长度是否真的由操作复杂度决定？
- 每个数字是否有执行依据，还是为了显得专业而补写？
- 删除碎碎念后是否信息仍完整？若完整且没有真实附言素材，就删除。
- 去掉形容词后，读者是否仍知道怎么做、做到什么状态？
- 是否复制了原帖的个人经历、读书笔记、价格、热量或品牌判断？若是，删除或重新取证。
- 本条是否把碎碎念与读书笔记混成了自创模块？
- 书籍附言是否只有书名加一句短笔记，并与菜谱保持独立？
- 是否固定套用了“今天吃 + ps. + 温柔感悟”，而不是由素材决定？
- 是否比 `publishing-copy-golden.md` 少了一人份用量、主菜关键时间、结束状态、配菜或主食做法？
- 是否存在只有菜名没有正文的空菜单段？
- 是否用一段泛化碎碎念遮住了菜谱信息不足？
